## はじめに

AIエージェントにcronジョブを任せると、いつか必ずぶつかる壁がある。「取り消せない操作をどう制御するか」だ。

X投稿、メール送信、外部APIへのPOST——これらは一度実行したら戻せない。人間がボタンを押すなら「本当にいいですか？」ダイアログで済むが、cronで自動実行されるエージェントにはそれがない。

本記事では、筆者が実際に**重複投稿事故**を起こした経験から構築した「preflight-gate」の設計と、複数AIエージェント体制でのクロスレビューの仕組みを紹介する。

---

## 背景：重複投稿事故が起きた日

2026年3月1日、X自動投稿ジョブ `x-auto-post` を手動トリガーした。OpenClaw（AIエージェント基盤）のcronタイムアウトが「CLI応答待ちのみ」でジョブ自体はキャンセルされないことを知らず、応答がないと思って2回叩いた。結果、同じ内容のポストが2件公開された。

原因は明確だった：
- cronのタイムアウト仕様を誤解していた
- 不可逆操作に対するゲートキーパーが存在しなかった

## 設計：preflight-gate の仕組み

### 基本アーキテクチャ

```
[cronジョブ] → [preflight-gate.sh] → 判定OK → [実行]
                     ↓ 判定NG
                 [Discord通知 + abort]
```

preflight-gateは、不可逆操作の直前に挟む「最終確認レイヤー」だ。具体的には以下の3つのチェックを行う。

### チェック1：1日1件制限

```bash
GATE_DIR="$HOME/.openclaw/workspace-watchdog/gate"
TODAY=$(date +%Y-%m-%d)
LOCK_FILE="$GATE_DIR/${OPERATION_TYPE}-${TODAY}.lock"

if [ -f "$LOCK_FILE" ]; then
  echo "BLOCKED: Already executed today"
  exit 1
fi
```

X投稿は1日1件ペースという運用方針を、スクリプトレベルで強制する。人間の判断ミス（2回叩き）もエージェントの暴走も、これで防げる。

### チェック2：10分ロック

```bash
RECENT_LOCK="$GATE_DIR/${OPERATION_TYPE}.recent"
if [ -f "$RECENT_LOCK" ]; then
  AGE=$(( $(date +%s) - $(stat -f %m "$RECENT_LOCK") ))
  if [ $AGE -lt 600 ]; then
    echo "BLOCKED: Too recent (${AGE}s ago)"
    exit 1
  fi
fi
touch "$RECENT_LOCK"
```

同一操作の連続実行を10分間ブロックする。手動の「もう1回」を物理的に防ぐ。

### チェック3：watchdog AIによる判定

ここが複数AI体制ならではのポイント。preflight-gateの実行主体は、メインAI（コンテンツ制作担当）ではなく、監視専門のwatchdog AIだ。

```
メインAI → 投稿したい → preflight-gate → watchdog AIが判定
```

watchdogは独立したワークスペースで動作し、メインAIとはモデルも権限も分離されている。「自分で作って自分で承認」を構造的に防いでいる。

## 複数AI体制でのクロスレビュー

### なぜ複数AIが必要か

単一AIによる自動化は「エージェントが間違えたら誰も止められない」という構造的欠陥を持つ。筆者の環境では以下の役割分担で運用している：

| エージェント | 役割 | モデル |
|---|---|---|
| メインAI | コンテンツ制作・投稿 | Gemini |
| watchdog AI | 監視・ゲートキーパー | Claude |

重要なのは**モデルが異なる**こと。同じモデルでラベルだけ変えても意味がない。実際にその失敗もした——3体目のエージェントを作ったが、メインAIと同モデル同権限で、ラベルだけ違う無駄なエージェントだった。即廃止した。

**エージェント追加の判断基準：モデル・権限・状態のどれかが独立していなければ、追加する価値はない。**

### watchdog-job-verify：事後検証

preflight-gateは事前チェックだが、watchdog AIには事後検証ジョブもある。毎日13:00に全ジョブの実行結果を検証し、異常があればDiscordに通知する。

```
13:00 watchdog-job-verify
  → 各ジョブのログを検査
  → FAIL/異常パターン検出
  → Discord通知（問題時のみ）
```

事前ゲート（preflight-gate） + 事後検証（job-verify）の二段構えで、不可逆操作の安全を担保する。

## 結果と学び

preflight-gate導入後：
- **重複投稿: 0件**（導入前は初日に発生）
- **意図しない本番操作: 0件**
- watchdogによるブロック実績: 手動の誤再実行を2回防止

もっとも大きな学びは、**安全設計はコードレビューやテストの問題ではなく、アーキテクチャの問題**だということ。単一エージェントにどれだけガードレールを書いても、そのエージェント自身がガードレールを無視できる時点で意味がない。独立した監視エージェントによる外部チェックが、自動化における安全の本質だ。

---

## まとめ

1. **不可逆操作には必ずゲートを挟む** — 1日1件制限 + 10分ロック + 外部AI判定
2. **監視と実行を同一エージェントにさせない** — モデル・権限・ワークスペースを分離する
3. **「ラベルだけ別」のエージェント追加は無意味** — モデル・権限・状態のどれかが独立していなければ追加する価値はない

cronで動くAIエージェントの安全設計は、人間のオペレーションにおける「ダブルチェック」や「承認フロー」と本質的に同じだ。ただし、AIの場合は人間よりはるかに速く・頻繁に動くため、ゲートもプログラマティックに実装する必要がある。
